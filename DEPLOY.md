# Deploying Commission Escrow (standalone) on Render

Exact ordered steps for the owner. The order matters most at step 7:
**the free Postgres expires 30 days after it is created**, so it is
created LAST, when the test window is actually opening. Everything
before that step is free to sit idle.

Local verification first (any machine with Bun):

```sh
bun install
bun run build      # client bundle + server bundle + both typechecks
bun test tests/    # 59 tests: hash parity, authorization matrix, e2e walks
bun run db:seed-demo   # optional local demo (PGlite + local storage)
bun run start      # http://localhost:3000
```

## Step 1 — GitHub repo (owner creates)

1. Create a **private** GitHub repository (suggested name:
   `commission-escrow`).
2. Push this `standalone/` directory as the repo root (it contains
   `Dockerfile`, `render.yaml`, `package.json`, `bun.lock`).
3. Never commit a filled `.env` — `.env.example` lists names only.

## Step 2 — Object storage bucket (owner creates, Cloudflare R2)

1. In Cloudflare: R2 → Create bucket (suggested name:
   `commission-escrow-media`). Keep it **private** — no public access,
   no r2.dev subdomain. The app serves every byte itself after its
   authorization checks; a public bucket would defeat that.
2. R2 → Manage API Tokens → create a token scoped to that bucket
   (Object Read & Write). Note the Access Key ID + Secret Access Key.
3. Note the S3 endpoint: `https://<your-account-id>.r2.cloudflarestorage.com`.

## Step 3 — Render web service + cron (blueprint)

1. Create a Render account; connect the GitHub repo from step 1.
2. New → Blueprint → pick the repo. Render reads `render.yaml` and
   proposes two services: `commission-escrow` (web) and
   `commission-escrow-tick` (cron, every 5 minutes).
3. Fill the `sync: false` values it prompts for:
   - `OWNER_EMAIL` — your email (the account that will be born dev).
   - `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`,
     `S3_SECRET_ACCESS_KEY` — from step 2.
   - Leave `DATABASE_URL` **blank for now** on both services.
   - `APP_ENCRYPTION_KEY` is generated by Render automatically.
4. Apply the blueprint. The web service will deploy and start, but
   `/readyz` will report not-ready until the database exists — expected.
5. **Immediately suspend the cron service** (Render dashboard →
   `commission-escrow-tick` → Suspend). It stays suspended until step 10.

## Step 4 — (pause point)

Everything above can sit here indefinitely at no cost and with no
clock running. Continue when the beta test window is actually opening.

## Step 5 — Postgres, LAST (starts the 30-day clock)

1. Render dashboard → New → PostgreSQL. Name: `commission-escrow-db`.
   Plan: **Free**. Region: same as the web service (Oregon).
2. When it is created, copy its **Internal Database URL**.
3. Web service → Environment: set `DATABASE_URL` to that URL. Save —
   the service redeploys, runs migrations on boot, and `/readyz` turns
   green (`{"ok":true,"migrations":["0001_baseline.sql"]}`).
4. Cron service → Environment: set its `DATABASE_URL` to the same URL
   (leave the cron itself still suspended).
5. **Put two reminders on your calendar now: day 21 and day 28 after
   today.** The free database is deleted at day 30 unless you upgrade
   it or export and move. A weekly export (Render dashboard → database
   → Backups/Connect, or `pg_dump`) is cheap insurance.

## Step 6 — Seed the demo content (optional, recommended for the beta)

**Hosted route (used for the launch deploy):** set the web service's
`SEED_DEMO_ON_BOOT` env var to `1` before the first deploy with the
database attached. The container entrypoint runs the seed on boot,
then starts the app. **Remove the variable (or set it back to 0) as
soon as the site is up** — the seed tops invite codes back up to 10,
which must not happen once testers start spending them. The 10 codes
are then visible in the owner's Admin (Dev controls) after step 7.

**Local route (alternative):** from a local checkout with the
production `DATABASE_URL` and the S3 variables set in your shell
environment:

```sh
bun run db:seed-demo
```

It installs the 5 demo shops, posts, auction lot and demo jobs, stores
the demo media in the bucket, and prints **exactly 10 single-use invite
codes**. Treat those printed codes as secrets — save them somewhere
private; anyone holding one can sign up. (Re-running is safe: it
reports "already seeded" and tops the codes back up to 10.)

## Step 7 — Owner signup (bootstrap)

1. Open the Render URL. Sign up with the **same email you set as
   `OWNER_EMAIL`**. No invite code is needed for that one address —
   the account is born with the dev role.
2. Open Admin (Dev controls) and confirm: your account shows role
   `dev`, and the invite list shows exactly **10** codes (if you seeded
   in step 6). If you skipped the seed, generate your first codes here
   instead — but note the launch plan expects the seeded 10.

## Step 8 — First end-to-end job test

With a second browser/profile, sign up a tester artist and a tester
buyer using two of the invite codes, then walk one small job:
Brief → Quote → (crypto: artist lists a BTC/LTC/USDT wallet; buyer
sends from their own wallet and pastes the txid; the **simulated**
checker confirms it — it is labelled simulated in the job record, the
live checker is phase 2) → Sketch → Approve → Vault delivery → Balance
txid → automatic Unlock → buyer downloads the original. Confirm the
download count increments and standing lands (artist 85 / buyer 40 on
a clean first job).

## Step 9 — Enable the cron

Resume `commission-escrow-tick` in the Render dashboard. Confirm in the
database (or via a ghost-check test) that runs are being recorded in
`background_job_runs`.

## Step 10 — Notes for the test window

- **Cold starts:** the free web service sleeps after ~15 minutes idle;
  the first load can take about a minute. Tell testers, or upgrade the
  web plan if it annoys people.
- **Login throttle** is per-account (5 failures / 15 minutes) and live.
  A per-IP throttle was deliberately not built: behind Render's proxy
  the client IP needs a deliberate trust decision first. If abuse
  appears, that's the follow-up.
- **Backups:** export the database weekly during the window (see
  step 5). Media lives in R2 and survives independently.
- **The checker is simulated** in this phase — txid shape + job record
  only, honestly labelled in-product. Do not run real-money jobs on it.
  The live BTC/LTC/USDT-TRON checker is phase 2.
